## 1. CpuParticles2D with a 4096×4096 emission region (40–120 particles)

**Answer: fine; region size does not affect per-frame cost.** `EmissionRectExtents` only spreads spawn positions (used at particle birth in `cpu_particles_2d.cpp`); cost scales with `Amount` (CPU simulation) — docs: CPUParticles2D has "near-feature parity … but lower performance when using large amounts of particles"; 40–120 is trivial either way.
- **Offscreen processing:** CPU particles are simulated every frame while `emitting` and the node is visible in the tree; the update early-outs only on `particles.size() == 0 || !is_visible_in_tree()` — screen position is not checked (source). No per-particle culling; irrelevant at these counts.
- **Rendering:** the emitter is ONE canvas item, drawn internally as a MultiMesh (`canvas_item_add_multimesh` in `cpu_particles_2d.cpp`) — cannot cost one draw call per particle.
- **GPU vs CPU culling:** GPUParticles2D has `visibility_rect` (default `Rect2(-100,-100,200,200)`): "the node's region which needs to be visible on screen for the particle system to be active"; tutorial: "If this rectangle is outside of the viewport, the engine will not render the particles on screen." CPUParticles2D has **no** `visibility_rect` — source comment: "No visibility_rect property contrarily to Particles2D, it's updated automatically." For a 4096 arena, GPU particles need a grown rect or they deactivate when the emitter node leaves the screen; CPU particles have no such trap.
- **Ambiguity:** the 2D particles tutorial says Local Coords is "on by default", but the 4.3 class refs say `local_coords = false` for **both** CpuParticles2D and GpuParticles2D. Class refs win; `false` = world-space particles (good for ambient world dust). Verify in-game before relying.
- **C# names:** `CpuParticles2D.EmissionRectExtents`, `.Amount`, `.LocalCoords`, `.DrawOrder` (`DrawOrderEnum.Index|Lifetime`), `.Texture`.
- **Confidence:** mechanics Confirmed (T1/T2); "region size is free" Confirmed by source (no cost path uses extents beyond spawn).
- **Sources:** https://docs.godotengine.org/en/4.3/classes/class_cpuparticles2d.html · https://docs.godotengine.org/en/4.3/classes/class_gpuparticles2d.html · https://docs.godotengine.org/en/4.3/tutorials/2d/particle_systems_2d.html · https://raw.githubusercontent.com/godotengine/godot/4.3/scene/2d/cpu_particles_2d.cpp (lines 560, 1111, 1301)

## 2. 100–800 small procedural items: `_Draw` vs CpuParticles2D vs MultiMeshInstance2D

**Answer: one CanvasItem `_Draw` is the right tool at these counts; MultiMesh is for thousands; particles are wrong for static clutter.**
- **`_Draw`:** docs list "Drawing a large number of simple objects … Custom drawing avoids the overhead of using a large number of nodes"; `draw_polyline` is documented as "faster than using individual draw_line calls" for many lines. All commands of one item batch into few draw calls; 100–800 quads/dots/lines per frame is well within budget (no numeric threshold documented). **Confidence:** method Confirmed (T1); the "800 is fine" judgement = Community consensus.
- **MultiMeshInstance2D + MultiMesh:** "single draw primitive … up to millions"; class doc "draw thousands of instances with a single draw call". Documented costs: all-or-none visibility ("no screen or frustum culling possible for individual instances"; `CustomAabb` only) and — critical here — **"A MultiMesh is a single object, therefore the same maximum lights per object restriction applies … once the maximum lights are consumed by one or more instances, the rest of the MultiMesh instances will not receive any lighting."** No per-instance y-sort or collision.
- **2D setup (exact):** `MultiMeshInstance2D` (Node2D; `Multimesh` and `Texture` properties; texture is used by the default `CanvasItemMaterial` and readable as `TEXTURE` in canvas_item shaders — CanvasItem materials work). On the MultiMesh: set `TransformFormat = MultiMesh.TransformFormatEnum.Transform2D` **before** `InstanceCount`; write instances with `SetInstanceTransform2D`; `UseColors`/`UseCustomData` "can only be set when InstanceCount is 0 or less" (and must match `SetInstanceColor`/`SetInstanceCustomData`). Mesh must be 2D geometry (docs "2D meshes": "two-dimensional geometry (Z can be omitted or ignored)"; editor can convert Sprite2D→Mesh; QuadMesh/PlaneMesh/ArrayMesh all work in practice — QuadMesh in 2D = Community consensus).
- **Also available in 4.3:** `CanvasItem.DrawMultimesh(MultiMesh, Texture2D)` — one `_Draw` node can draw a MultiMesh directly ("Draws a MultiMesh in 2D with the provided texture"); it exists since 4.0 (verified in the 4.0 class XML).
- **Recommendation:** ground clutter → one `_Draw` (switch to `DrawMultimesh`/MultiMeshInstance2D above ~5k items); critters that y-sort/collide → individual Node2D (hundreds OK — avoid the per-object submission cost of ~800 Sprite2D only if profiling says so); thousands of non-sorted critters → MultiMesh. CpuParticles2D is not a clutter/critter substitute.
- **Sources:** https://docs.godotengine.org/en/4.3/tutorials/2d/custom_drawing_in_2d.html · https://docs.godotengine.org/en/4.3/classes/class_multimesh.html · https://docs.godotengine.org/en/4.3/classes/class_multimeshinstance2d.html · https://docs.godotengine.org/en/4.3/classes/class_canvasitem.html · https://docs.godotengine.org/en/4.3/tutorials/performance/using_multimesh.html · https://docs.godotengine.org/en/4.3/tutorials/2d/2d_meshes.html

## 3. PointLight2D per-item limit in 4.3 (and popping)

**Answer: yes — 16 lights per CanvasItem, per item, not per "region".** Engine constant `#define MAX_LIGHTS_PER_ITEM 16` (Forward+ `canvas_uniforms_inc.glsl`; Compatibility `uint(16)`), shader comment "max 16 lights" (canvas.glsl), and maintainer clayjohn on #81147: "The 2D renderer supports up to 16 lights per item … the 16 light limit applies to the entire [TileMap] quadrant." Godot 4 2D has no light clusters/regions — a "region" only matters when nodes merge into one item (a TileMap quadrant is one item per #81147; a MultiMesh is one object for all its instances; CanvasGroup children stay separate items during the group's internal pass).
- **Source nuance (4.3 Forward+):** the per-item light list is packed with a 4-bit count and the pack loop stops at `MAX_LIGHTS_PER_ITEM - 1`, so the implementation effectively packs ≤15 positional lights per item (directional lights are counted separately). Docs/maintainers say 16. **Treat ~15 as the actionable ceiling; do not design to exactly 16.** (Ambiguity flagged; Compatibility renderer internals not verified at this level.)
- **Exceeding the cap:** not documented; source silently stops adding lights (no error). Which lights survive is unspecified → possible popping/discontinuities as membership changes with movement. **Confidence:** cap Confirmed (T1/T2); popping = Uncertain (no official statement found).
- **CanvasModulate is not a light** and consumes no slot (it is a canvas-wide tint).
- **For Hero-sArena:** the existing 12-slot flash pool + ambient stays under the cap only if all overlap the same item; the MultiMesh note in §2 means one MultiMesh ground layer shares a single 16-light budget for all its instances.
- **Sources:** https://github.com/godotengine/godot/issues/81147 · https://raw.githubusercontent.com/godotengine/godot/4.3/servers/rendering/renderer_rd/shaders/canvas_uniforms_inc.glsl · https://raw.githubusercontent.com/godotengine/godot/4.3/servers/rendering/renderer_rd/shaders/canvas.glsl · https://raw.githubusercontent.com/godotengine/godot/4.3/servers/rendering/renderer_rd/renderer_canvas_render_rd.cpp

## 4. Y-sorting for top-down in 4.3

**Answer: use `CanvasItem.YSortEnabled` (C#) on the arena root; each CanvasItem is one sort unit.** Docs verbatim: "this and child CanvasItem nodes with a higher Y position are rendered in front of nodes with a lower Y position"; "Nodes sort relative to each other only if they are on the same z_index"; nested rule — with Y-sort on parent 'A' and off on child 'B', "the child node ('B') is sorted but its children (C1, C2, etc) render together on the same Y position as the child node ('B')".
- Sorting uses the node's global Y (origin): a custom `_Draw` node sorts as a whole; a particle emitter sorts as a whole. **No per-particle y-sort** — CPUParticles2D `DrawOrder` is only `Index|Lifetime`, GPUParticles2D adds `ReverseLifetime`; those order particles inside the emitter, nothing more.
- **Mixing practicalities:** `z_index` layers win over y-sort (docs), so keep ground clutter at a lower z_index / separate non-sorted node and actors in the y-sorted root; give each actor a single Node2D root at "foot" position so its sprites/particles sort together. Origin-at-feet is not a docs statement — standard practice.
- **Confidence:** sort semantics Confirmed (T1); mixing recipe = Community consensus.
- **Sources:** https://docs.godotengine.org/en/4.3/classes/class_canvasitem.html · https://docs.godotengine.org/en/4.3/classes/class_cpuparticles2d.html · https://docs.godotengine.org/en/4.3/classes/class_gpuparticles2d.html

## 5. Deterministic randomness in C#

**Answer: `RandomNumberGenerator` with an explicit `Seed` for gameplay RNG; a stateless integer hash of coordinates for per-position content; never `Random.Shared`/parameterless `Random`.**
- Godot docs: "A given seed will give a reproducible sequence of pseudo-random numbers" (`Seed`), but "It currently uses PCG32. **Note: The underlying algorithm is an implementation detail and should not be depended upon**" — reproducible within a Godot version, not a cross-version contract. Also: "The RNG does not have an avalanche effect … use a hash function to improve your seed quality"; set `Seed` before touching `State` (setting Seed mutates state).
- .NET: `new Random(seed)` in .NET 8 deliberately keeps the legacy algorithm ("we still need to respect the same algorithm that's been used in the past" — runtime source comment), so seeded sequences are stable on the .NET line; the parameterless ctor uses Xoshiro and is **not** reproducible. Microsoft docs only guarantee "If the same seed is used for separate Random objects, they will generate the same series".
- **Per-position values:** don't thread one sequential RNG through world generation — use a stateless hash of `(x, y, salt)` (splitmix64 / PCG hash, ~5 lines of C#) so any tile is reproducible independently and across versions. `GD.Hash(variant)` / `String.Hash()` exist but have no documented cross-version stability promise.
- **Gotcha:** CPUParticles2D emission randomness uses the engine global RNG (`Math::randf()` in the source), not your seeded RNG — never derive gameplay outcomes from particle trajectories.
- **Confidence:** quotes Confirmed (T1); recommendation = Community consensus. .NET seeded-sequence stability = Confirmed (T2, .NET source).
- **Sources:** https://docs.godotengine.org/en/4.3/classes/class_randomnumbergenerator.html · https://docs.godotengine.org/en/4.3/tutorials/math/random_number_generation.html · https://github.com/dotnet/runtime/blob/release/8.0/src/libraries/System.Private.CoreLib/src/System/Random.cs · https://learn.microsoft.com/en-us/dotnet/api/system.random?view=net-8.0

## 6. Parallax2D in 4.3 (top-down suitability)

**Answer: available in 4.3, but marked Experimental; works for any camera direction, so it is usable for top-down haze.**
- 4.3 release notes announce the Parallax2D node. Class doc: "**Experimental:** This node is meant to replace ParallaxBackground and ParallaxLayer. The implementation may change in the future." The 4.3 2D Parallax tutorial: "This page only covers how to use Parallax2D. This node is still experimental". In 4.3 the old nodes are **not yet marked deprecated** in their class pages (the "Deprecated: Use the Parallax2D node instead" banner appears only in later/stable docs).
- Mechanics: camera-relative via `scroll_scale` (1 = camera speed, <1 = further, 0 = static), plus `autoscroll` (px/s) and `repeat_size`/`repeat_times` for infinite repeat; `ignore_camera_scroll` for manual control. Nothing is side-scroller-specific — for a top-down drifting haze/starfield, `scroll_scale` slightly <1 plus `autoscroll` covers it; if you want drift fully decoupled from the camera, a plain item with a TIME-based shader offset is simpler.
- **C# names (verified):** `Parallax2D.Autoscroll`, `.ScrollScale`, `.ScrollOffset`, `.ScreenOffset`, `.RepeatSize`, `.RepeatTimes`, `.IgnoreCameraScroll`, `.FollowViewport`, `.LimitBegin`, `.LimitEnd`.
- **Confidence:** availability/status Confirmed (T1); "suitable for top-down" = no documented limitation, reasoned (Community consensus).
- **Sources:** https://godotengine.org/releases/4.3/ · https://docs.godotengine.org/en/4.3/classes/class_parallax2d.html · https://docs.godotengine.org/en/4.3/tutorials/2d/2d_parallax.html · https://docs.godotengine.org/en/stable/classes/class_parallaxbackground.html

## 7. Can PointLight2D light a custom `_Draw`ed CanvasItem? (`light_mode`)

**Answer: yes — all CanvasItems are lit by default, including untextured custom drawing.** The canvas fragment shader runs its light loop and multiplies the light by the item's base color (`light_color.rgb *= base_color.rgb`), where base color is the drawn vertex/texture color — so `draw_rect`/`draw_polygon`/`draw_line` output receives light with no texture on the item. Requirements: item `light_mask` (`CanvasItem.LightMask`) intersects the light's `range_item_cull_mask`, item Z inside the light's Z range, same canvas.
- **Opting out/in:** `CanvasItemMaterial.LightMode` — `LightModeEnum.Normal` (default, lit), `LightModeEnum.Unshaded` ("Render the material as if there were no light"), `LightModeEnum.LightOnly` ("Only draw on light pass"); equivalent ShaderMaterial `render_mode unshaded` / `light_only`. The 4.3 lights tutorial assumes items are lit by default; the enum wording lives in the class refs.
- PointLight2D itself: "This light's shape is defined by a (usually grayscale) texture" — assign a radial texture (see sibling `godot-43-2d-lighting.md` for a code-generated `GradientTexture2D`).
- **Confidence:** Confirmed (T1/T2).
- **Sources:** https://docs.godotengine.org/en/4.3/classes/class_canvasitemmaterial.html · https://docs.godotengine.org/en/4.3/tutorials/2d/2d_lights_and_shadows.html · https://docs.godotengine.org/en/4.3/classes/class_pointlight2d.html · https://raw.githubusercontent.com/godotengine/godot/4.3/servers/rendering/renderer_rd/shaders/canvas.glsl

## 8. BlendMode.Add vs Light2D vs CanvasModulate

- **Add-blended items still go through the light pass** (blend mode is output blend state; the light loop is in the same shader), but additive can only brighten: lighting an additive item adds brightness and it can never be darkened/shadowed. Use add for sparks/glow only.
- **CanvasModulate gotcha:** it "applies a color tint to **all** nodes on a canvas" and is implemented as a canvas-wide modulate multiplied into every item. Therefore additive particles inside a darkened canvas are multiplied down too (dim sparks), and `unshaded` does **not** exempt them (modulate applies regardless of `light_mode`). Reliable fix: keep the additive FX on a separate `CanvasLayer` **without** CanvasModulate ("CanvasLayers can be used to render things independently") — but note lights on the game canvas do not light items on another CanvasLayer unless placed there.
- **Confidence:** multiply mechanics Confirmed (T1 docs + renderer source); "sparks look dim" is the standard consequence (Community consensus); no official issue/warning found — verify visually.
- **Sources:** https://docs.godotengine.org/en/4.3/classes/class_canvasmodulate.html · https://docs.godotengine.org/en/4.3/tutorials/2d/2d_lights_and_shadows.html · https://raw.githubusercontent.com/godotengine/godot/4.3/servers/rendering/renderer_canvas_cull.cpp

## 9. `_Draw` + `QueueRedraw` performance (~500 lines/frame)

- Docs: "The `_draw` function is only called once, and then the draw commands are cached and remembered"; call `CanvasItem.QueueRedraw()` (C#) when data changes; redrawing every frame from `_process` is a **documented, supported** pattern (full C# example in the tutorial). `draw_polyline` is documented faster than many `draw_line` calls; custom drawing is the documented approach for "a large number of simple objects" to avoid node overhead.
- **No numeric budget is documented** for 4.3 (docs are silent on N lines/frame) — this is an explicit doc gap. Community consensus: ~500 simple primitives re-recorded per frame in one item is cheap (one item's command buffer, a few thousand vertices); profile if it ever regresses.
- **Best pattern for wind/twinkle:** keep geometry static and animate a canvas_item shader uniform (e.g. `TIME`) so `_Draw` is never re-run; or use `DrawMultimesh` and rewrite only the instance buffer when data actually changes.
- **Confidence:** docs quotes Confirmed (T1); numbers = Community consensus/Uncertain.
- **Sources:** https://docs.godotengine.org/en/4.3/tutorials/2d/custom_drawing_in_2d.html · https://docs.godotengine.org/en/4.3/classes/class_canvasitem.html

## 10. Wind without per-frame redraw (canvas_item vertex shader in 4.3)

**Answer: confirmed — canvas_item vertex shaders can offset `VERTEX` in 2D in 4.3.** Built-ins: `inout vec2 VERTEX` ("Vertex data (`VERTEX`) is presented in local space (pixel coordinates, relative to the Node2D's origin)"; `inout` = writable) and global `in float TIME` ("time since the engine has started, in seconds … not affected by time_scale or pausing", 3600 s rollover — add your own uniform if pausable wind is needed). Typical: `void vertex() { VERTEX.x += sin(TIME * 1.7 + VERTEX.y * 0.05) * 6.0; }`.
- **Geometry caveat:** `vertex()` runs per vertex of the item. A `Sprite2D` is a 4-vertex quad — offsetting verts shears the whole sprite, it cannot sway individual blades. For per-blade motion inside one shader: use geometry with more vertices — `Polygon2D`/`Line2D` (real per-point verts), or `MeshInstance2D`/`MultiMeshInstance2D` with a subdivided mesh (docs: MeshInstance2D displays a Mesh in 2D; "2D meshes are meshes that contain two-dimensional geometry (Z can be omitted or ignored)"). Cheapest for a baked tuft/pebble texture layer: fragment-shader UV distortion by `TIME` (no geometry needed).
- **CanvasGroup caveat:** "Child CanvasItem nodes of a CanvasGroup are drawn as a single object" (flattened backbuffer) — one shader on the CanvasGroup moves the merged quad as a whole, **not** its children individually; children keep their own shaders during the internal pass. Also CanvasGroup + `CanvasItem.clip_children` "will not function correctly" (docs).
- **Confidence:** `VERTEX`/`TIME` Confirmed (T1); geometry-count behavior Confirmed (docs + well-known); specific sway recipe = Community consensus.
